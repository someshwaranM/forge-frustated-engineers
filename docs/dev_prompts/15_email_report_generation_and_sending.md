# VIGIL — Phase 15 Dev Prompt: Email Report Generation & Sending

## 1. Purpose

Phase 15 adds an enterprise-style **RM Compliance Report Email** workflow to Vigil.

From the RM Analytics detail page:

`/rm-analytics/<rm_id>`

the reviewer can click:

**Send Report on Mail**

A modal allows the reviewer to select a recipient from available Vigil/user email addresses or enter a custom email address.

Vigil then:

1. validates the RM,
2. gathers authoritative RM analytics, call, finding, and case data,
3. generates a polished responsive HTML compliance report,
4. sends the report through the configured SMTP/email provider,
5. records the report-send activity for auditability,
6. returns a clear success/failure response to the frontend.

The report must be visually impressive, readable, detailed, and suitable for an enterprise BFSI compliance workflow.

# 9. Email Delivery via Elastic Kibana Connector

Vigil does **not** speak SMTP directly. A Kibana email connector has already been created and configured outside of Vigil:

```text
Connector name : vigil-mail
Connector ID   : vigil-mail
Sender         : pranika2525@gmail.com
Service        : Gmail
Host           : smtp.gmail.com
Port           : 465
Allow HTML content : enabled
```

The SMTP host/port/credentials live inside this Kibana connector's own configuration — Vigil's backend never sees or stores them. `email_service.py` sends the report by calling Kibana's **Run connector** API:

```http
POST {KIBANA_BASE_URL}/api/actions/connector/vigil-mail/_execute
Content-Type: application/json
kbn-xsrf: true
Authorization: ApiKey {ELASTIC_API_KEY}
```

Body:

```json
{
  "params": {
    "to": ["audit.officer@vigil.com"],
    "subject": "[Vigil] RM Compliance Report — Rahul Desai (RM005)",
    "message": "<plain-text/markdown fallback body>"
  }
}
```

Environment variables (replace Section 9's original SMTP_* block entirely — Vigil holds no SMTP credentials):

```env
KIBANA_BASE_URL=<KIBANA_BASE_URL>
KIBANA_CONNECTOR_ID=vigil-mail
ELASTIC_API_KEY=<ELASTIC_API_KEY>
EMAIL_REQUEST_TIMEOUT_SECONDS=20
```

The API key used here only needs **read privileges on the Actions and Connectors feature** (per Elastic's documented prerequisite for the execute-connector API) — do not provision it with broader cluster privileges than that.

### ⚠ Open question — must be verified before building the full HTML renderer

The Kibana email connector's officially documented `_execute` params are `to`, `cc`, `bcc`, `subject`, and `message` (Markdown-supported plain text that Kibana auto-renders into simple plain+HTML). The "Allow HTML content" toggle on the connector suggests raw custom HTML is deliverable, but Elastic's alerting team has, in at least one Kibana version, deliberately restricted sending **raw arbitrary HTML bodies** to Kibana's internal "notifications" mechanism only — explicitly *not* via the public `_execute` HTTP route — as a deliberate security decision (to prevent the execute API from becoming a generic HTML-injection mail relay).

This directly affects whether Section 11's "polished, card-based, branded HTML report" is achievable as designed through this connector, or whether the connector will only accept Markdown-derived formatting (headings, bold, links, simple lists — no custom CSS, no card layout, no severity badges).

**Before building `rm_report_renderer.py`, do a one-off spike:** call `_execute` on `vigil-mail` with a `messageHTML` field (or whatever field the currently-installed Kibana version actually documents/accepts) containing real HTML, and confirm by inspecting the received email whether it renders as HTML or is stripped to the plain-text fallback. The outcome decides:

- **If raw HTML is accepted:** Section 11 proceeds as written.
- **If raw HTML is rejected/stripped:** the report renderer must instead produce a well-structured **Markdown** document (still following Section 35's visual hierarchy and Section 15–19's content requirements), and Section 11 must be scoped down to "polished Markdown-rendered email" rather than custom HTML/CSS. This is a real possibility on the currently-installed Kibana version and should be resolved with a 5-minute test rather than assumed either way.

Do not silently fall back to plain SMTP as a workaround if this connector can't do rich HTML — that would bypass the explicit instruction to use the Elastic connector. Flag it and get a decision instead.

This feature handles employee/customer/compliance information.

### Authentication

The endpoint must require an authenticated Vigil user.

### Authorization

Use the existing Phase 14 access model.

- RM name
- customer name
- transcript evidence
- case notes
- reasoning
- recommended action

# 44. Failure Scenarios

Explicitly test:

### Kibana connector unreachable / `_execute` returns an error

Kibana's execute response includes a `status` field (`ok` or `error`) and, on error, a `message`/`service_message`. Map any non-`ok` status, non-2xx HTTP response, or request exception (timeout, connection refused) to:

```text
502 EMAIL_SEND_FAILED
```

No false success. Log the raw Kibana response body server-side (Section 45) for debugging; never forward it verbatim to the frontend.

### Invalid recipient

Expected:

```text
422 INVALID_RECIPIENT
```

No call to `_execute` at all — validate before touching the connector.

### RM doesn't exist

Expected:

```text
404 RM_NOT_FOUND
```

### `ELASTIC_API_KEY` missing/invalid or connector ID wrong

Kibana will return 401/403 (bad key) or 404 (unknown connector ID) from `_execute`. Both map to `502 EMAIL_SEND_FAILED` at the Vigil API boundary — do not leak which one occurred to the frontend, but log the distinction server-side since they need different fixes.

### Kibana/network timeout

Bound the HTTP call with `EMAIL_REQUEST_TIMEOUT_SECONDS`. On timeout, return the same controlled failure and log provider-side details server-side.

### HTML rendering error

Do not send a partial/invalid report.

### HTML rendering error

Do not send a partial/invalid report.

# 52. Review Addendum — Recommended Enhancements

The spec above is comprehensive. The gaps below are things a reviewer would likely flag in a BFSI compliance context or during real implementation, and are not already covered elsewhere in this document.

## 52.1 External-domain data-leakage guard (Custom Email option)

Section 6 lets a reviewer type any custom address, and Section 15–19 puts customer names, transcript evidence, and case details into that email. Nothing currently stops a compliance report from being sent to a personal/external address.

Add:

- An `internal_domains` allow-list (env: `VIGIL_INTERNAL_EMAIL_DOMAINS=vigil.com`) used only to classify, not to block outright — the hackathon should still allow one deliberate "external" demo case.
- When the custom email's domain is not in the allow-list, the modal must show an explicit inline warning before Send is enabled, e.g. `⚠ This address is outside your organization. The report contains customer and compliance data.`
- Log `recipient_domain_class=internal|external` on the audit event (Section 25) so this is reviewable after the fact, not just enforced at click time.

This is the single most likely finding a BFSI reviewer would raise about a "send compliance data to any email" feature, so it deserves a first-class field, not just a client-side note.

Separately: check whether the Kibana instance hosting `vigil-mail` has `xpack.actions.email.domain_allowlist` set at the platform level. If it is, Kibana itself will reject any recipient domain not on that list — independent of anything Vigil does — and that failure needs to map to a clear `INVALID_RECIPIENT`/`EMAIL_SEND_FAILED` distinction rather than looking like a generic connector error.

## 52.2 Header/CRLF injection on subject and recipients

Section 24 says "do not accept arbitrary mail headers from the client," but doesn't say how. Explicitly require:

- Reject any recipient or (if ever client-influenced) subject value containing `\r` or `\n` before it's placed into the `_execute` request body, not just at the email-syntax-validation step — email-regex validation alone does not guarantee this, and Kibana/the underlying SMTP layer should not be relied on as the only backstop.
- Since Section 10 already keeps the subject fully server-generated from RM name, this only matters if RM name itself could contain control characters — sanitize RM name/customer name once at the report-data layer (Section 8), not per-render, so both the email and any future PDF/download path inherit the fix.

## 52.3 Non-blocking connector call

Now that sending goes through Kibana's `_execute` HTTP API (Section 9) rather than raw `smtplib`, the transport is naturally a single outbound HTTPS request — use an async client (`httpx.AsyncClient`) with `EMAIL_REQUEST_TIMEOUT_SECONDS` as a hard timeout, `await`ed directly inside the async route. This is simpler than the threadpool workaround a blocking SMTP library would have needed, but the timeout still matters: an unresponsive Kibana instance must not hang the request indefinitely, per Rule 18 (Section 48).

## 52.4 One bounded retry on transient connector failure

Section 44 maps a Kibana `_execute` failure straight to `502 EMAIL_SEND_FAILED`. Transient failures (Kibana momentarily unreachable, connection reset, timeout) are common enough that a single retry avoids most false failures in a live demo:

- One retry, short fixed delay (e.g. 2s), only for timeout/connection-class errors — not for a `4xx` from Kibana (bad API key, unknown connector ID, malformed params), which will not succeed on retry and should fail immediately.
- Log both attempts; report only the final outcome to the frontend and audit log.

## 52.5 Request-level idempotency, not just a disabled button

Section 26's "disable the Send button" only protects against a second click — it does not protect against the browser retrying the same POST after a network blip, or a double-submit from an impatient reviewer refreshing mid-request. Add an `Idempotency-Key` (or `request_id`) generated client-side per modal-open and sent with the request; the backend should treat a repeated key for the same `rm_id` within a short window (e.g. 60s) as a no-op returning the original result rather than sending twice.

## 52.6 Indic-script rendering in the report

RM call data spans Tamil, Hindi, and English + Hindi/Tamil (per the demo dataset). Section 15/16 render customer names and transcript evidence directly from `transcript_original_text`, which will contain Devanagari/Tamil script. Add explicitly to Section 11/36:

- `<meta charset="UTF-8">` in the report `<head>`.
- A font-family fallback stack that includes generic Indic-capable fallbacks (e.g. `-apple-system, "Noto Sans", "Noto Sans Devanagari", "Noto Sans Tamil", sans-serif`) rather than assuming Latin-only rendering, since Section 11 already forbids requiring external fonts — this is about graceful fallback, not loading a webfont.

## 52.7 Distinguish "no calls yet" from "clean"

Section 20 defines a clean report (calls exist, none flagged). Add a distinct third state for an RM with zero calls in the system at all — e.g. a newly onboarded RM — so the report doesn't imply "reviewed and clean" when nothing has actually been reviewed yet:

```text
No calls have been recorded for this RM in the current reporting period.
```

## 52.8 Role check beyond "authenticated"

Section 31 says "only authenticated users with access to RM Analytics can send reports," which is good, but if Phase 14's auth model has any role/permission distinction at all (even a simple reviewer/admin flag), gate this specific action on it explicitly rather than on authentication alone — sending a compliance report externally is a more sensitive action than viewing analytics, and the two shouldn't necessarily share the same authorization bar. If Phase 14 has no roles yet, note this as a known limitation rather than skip it silently.

None of the above requires new architecture, new dependencies, or scope creep into Sections "Out of scope" — each is a small addition inside the existing `reports/` and modal design.
